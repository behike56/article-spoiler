# 有料テキスト記事の取得設計

## 概要

購読者が閲覧できる Substack の有料テキスト記事を、記事 URL から Markdown と画像としてローカルに保存する。ログインは利用者が専用ブラウザで行い、CLI はそのブラウザの認証状態を再利用する。RSS は記事 URL の発見にのみ使う。RSS に有料記事の全文が含まれることは前提にしない。

`auth login` と `fetch`、Chrome 拡張機能による ZIP 保存と `import` は実装済み。`sync` と全文の自動判定は未実装である。現在は利用者がブラウザで全文を確認してから保存する。

## 確認できた前提

- 現行 CLI は `input/*.html` を読み、対応する `_files/` ディレクトリから画像をコピーする。[`main.py`](../src/article_spoiler/main.py)、[`extract.py`](../src/article_spoiler/extract.py)
- Substack は出版物の公開 RSS を `<出版物の URL>/feed` と案内している。[Substack の RSS 案内](https://support.substack.com/hc/en-us/articles/360038239391-Is-there-an-RSS-feed-for-my-publication)
- 有料記事の無料読者向け表示にはプレビューや購読案内があり得る。[Substack の有料記事プレビュー](https://support.substack.com/hc/en-us/articles/4407989020308-How-do-I-publish-a-free-preview-of-a-paid-post-on-Substack)
- Playwright は認証状態を保持する専用ブラウザプロファイルを開ける。通常の Chrome プロファイルの直接操作はサポート対象外とされている。[Playwright BrowserType](https://playwright.dev/python/docs/api/class-browsertype)
- ブラウザの認証状態には機密性の高い Cookie 等が含まれる。[Playwright Authentication](https://playwright.dev/python/docs/auth)

Substack の公開 RSS に有料テキスト記事が掲載される条件、掲載される本文の範囲、ログイン済みページの DOM 構造は、対象の出版物と記事で未確認である。

## 対象範囲

- 利用者が正規に閲覧できる有料テキスト記事を、URL 指定で1件ずつ保存する。
- 将来、公開 RSS から記事 URL を列挙し、同じ取得処理を順番に実行する。
- 既存のローカル HTML 入力を維持する。

ログインの自動入力、購読契約の作成、アクセス制限の回避、音声・動画記事の保存は対象外とする。

## 利用者の操作と CLI

以下は予定するインターフェースである。既存の引数なし実行と `--input` / `--output` はそのまま使えるようにする。

```bash
uv run article-spoiler auth login
uv run article-spoiler fetch 'https://example.substack.com/p/article-slug'
uv run article-spoiler sync --feed 'https://example.substack.com/feed'
```

1. `auth login` は CLI 専用のブラウザプロファイルで可視ブラウザを開く。利用者が自分で Substack にログインし、CLI に戻って完了を伝える。CLI はパスワードや認証コードを受け取らない。
2. `fetch` は同じプロファイルで記事を開く。購読権限で本文を表示できる場合だけ Markdown と画像を保存する。
3. `sync` は RSS から URL を収集し、各 URL に `fetch` 相当の処理を適用する。未収録、取得不能、プレビューのみの記事を別々の結果として報告する。

`auth login` と `fetch` は先に実装する。`sync` は RSS の実データを確認した後に追加する。既存の `make run` はローカル HTML 入力を引き続き呼び出す。

## 処理の分割

```text
記事 URL ──→ 認証済みブラウザ ──→ 表示本文・画像 URL ──→ 共通記事モデル ──→ Markdown・画像
RSS ──→ 記事 URL の列挙 ──────┘
保存済み HTML + _files/ ──→ ローカル入力アダプタ ────────┘
```

- **取得**: Playwright の永続プロファイルで記事を開き、描画後の本文と画像参照を読む。Substack の非公開 API や内部 JSON の構造には依存しない。
- **判定**: 現在は利用者がブラウザで全文を確認する。本文未検出の場合は保存しない。ログイン画面、購読案内、プレビューの自動判定は今後、購読できる記事を使った実地検証で条件を確立する。
- **変換**: タイトル、本文ブロック、画像 URL、元記事 URL を共通記事モデルにまとめる。既存のローカル HTML 処理も同じ Markdown 出力側へ接続する。現在の `post-title` / `body markup` と `_files/` 前提は入力アダプタ内に閉じる。
- **画像**: 表示された記事本文の画像だけを対象とし、実際の URL を使って取得する。URL のクエリや同名ファイルによる衝突を避け、取得失敗を記事の結果に含める。
- **保存**: 正規化した記事 URL を識別子に使い、タイトル由来のディレクトリ名が衝突しても別記事を上書きしない。本文と必要な画像を一時ディレクトリに揃えてから出力先へ移し、失敗時に完成済み記事として扱わない。再実行時は記事識別子でスキップする。

## 認証状態と保存データ

- CLI 専用プロファイルはリポジトリ外の利用者データ領域に置く。作成時は本人だけが読める権限にし、パスを指定できるようにする。通常利用のブラウザプロファイルや Cookie を読み取らない。
- プロファイル、Cookie、ページ HTML、認証付き URL、ネットワーク記録を Git や通常ログに出さない。認証期限切れなら再ログインを案内する。
- 記事 URL と遷移後の URL、画像 URL は HTTPS と公開アドレスを確認する。画像取得はリダイレクトを追跡せず、Content-Type とサイズを確認する。ブラウザの途中のリダイレクトや DNS の変化の検証は未実装であり、信頼できる記事 URL を指定する。
- 新規の出力先は利用者だけが読める権限で作る。既存の出力先の権限は変更しない。`output/` は現在 Git の追跡対象から除外されている。
- 利用者が全文を確認できない場合は保存を中止する。購読状態やプレビューの自動判定は未実装である。

## 設計判断と代替案

| 方法 | 判断 | 理由 |
| --- | --- | --- |
| 専用ブラウザプロファイル | 採用 | 利用者の対話的ログインと認証状態の再利用ができる。ブラウザ起動の負荷はある。 |
| RSS の本文を直接変換 | 採用しない | 有料記事の全文が RSS にあることを確認できていない。 |
| HTTP クライアントに Cookie を渡す | 初期実装では採用しない | 認証情報の複製と保管を増やす。ページの表示条件もブラウザと異なる可能性がある。 |
| 通常利用のブラウザプロファイルを操作 | 採用しない | 他の閲覧データへアクセスし得るうえ、Playwright も既定の Chrome プロファイルの自動操作を推奨していない。 |

## ログイン済み Chrome のタブを使う案

専用ブラウザで CAPTCHA を完了できない場合に備え、Chrome 拡張機能を追加する案を推奨する。利用者は普段の Chrome で記事の全文を表示し、拡張機能のボタンを押す。拡張機能は選択中のタブからタイトル、表示された本文、画像参照を取り出す。本文が全文かどうかは利用者が確認する。

`activeTab` と `scripting` を用いると、利用者が拡張機能を実行したタブに一時的にアクセスできる。[Chrome の activeTab の説明](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab) 拡張機能は実装済みで、テスト用 Chromium と記事・画像のサンプル応答で ZIP 生成と CLI 変換を確認した。Substack の実記事と Chrome の許可ダイアログでの検証はまだ行っていない。

拡張機能と既存 CLI の受け渡し方法には二つの候補がある。

- **ファイル経由**: 拡張機能が記事データと取得できた画像を ZIP にまとめ、Chrome のダウンロード機能で保存する。CLI に ZIP のパスを渡して Markdown へ変換する。初期実装の候補とする。Chrome のダウンロード API はダウンロード先を任意の絶対パスとして指定できないため、CLI の `input/` に直接保存されるとは限らない。[Chrome downloads API](https://developer.chrome.com/docs/extensions/reference/api/downloads)
- **Native Messaging**: 拡張機能からローカルの CLI へ直接渡す。ダウンロード後のパス指定を省けるが、拡張機能とホストの登録が必要になる。[Chrome Native Messaging](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)

初期案では Cookie やプロファイルをエクスポートせず、選択した記事のデータだけを渡す。画像が他のドメインにある場合、ブラウザのアクセス制約や認証の影響で取得できるかは未確認である。失敗した画像は明示し、取得できていない画像を含む ZIP を完全な記事として扱わない。ZIP 自体にも有料記事が含まれるため、保存場所と削除方法を利用者に案内する。

現在は画像配信元のホストごとに追加のアクセス許可を要求し、拡張機能の画面から Cookie を付けずに画像を取得する。画像の取得に失敗すると ZIP を作らない。記事データは拡張機能のセッションストレージに一時保管し、ダウンロード開始後に削除する。画像配信元への許可は Chrome 側に保持されるため、不要になった許可は拡張機能の設定から削除できる。ZIP は非圧縮形式で、CLI はエントリの名前、容量、形式を検証し、ディレクトリへ直接展開しない。

別案として Chrome 144 以降の DevTools 自動接続がある。既存の Chrome に接続できるが、リモートデバッグの有効化と接続時の許可が必要で、接続先は他のタブや認証状態にもアクセスできる。[Chrome DevTools の接続案内](https://developer.chrome.com/docs/devtools/agents/get-started/configuration) CLI としての接続・配布方法は未検証であり、選択した記事を保存する用途では拡張機能を先に検討する。

実装前に、購読中の記事で本文と画像の取得、プレビュー表示、画像取得失敗時の動作を確認する。既存の専用ブラウザ方式とローカル HTML 方式は引き続き利用できるようにする。

## 実装順序と検証

1. 利用者が購読中のテキスト記事を1件用意し、ログアウト時とログイン時の表示、画像 URL、本文の終端を比較する。実記事や認証情報はテストリポジトリに含めない。
2. 専用プロファイルのログインと `fetch` を実装する。公開記事、購読可能な有料記事、権限のない記事、期限切れセッションで結果を確認する。
3. 共通記事モデルと原子的な保存処理を追加し、既存 HTML 入力の出力が変わらないことを確認する。
4. 対象出版物の RSS で有料記事の掲載状況を確認してから `sync` を実装する。RSS にない記事は URL 指定で扱う。

## 要確認

- 対象出版物の RSS に有料テキスト記事の URL が掲載されるか。
- ログイン後のページから全文とプレビューを安定して区別できるか。区別できない場合は利用者の確認を挟む運用が必要になる。
- 利用者が求める取得単位は、単一記事 URL、出版物全体の新着、または両方か。
- 保存先の既存記事を更新する必要があるか。初期案は再取得時にスキップする。
